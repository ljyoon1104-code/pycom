# 3단원 교과서 소스 호환성 감사

## v1.2.0 교과서 연계 페이지 재조사 (2026-09-14)

원본 3단원 56개를 다시 읽고 현재 VM으로 실행했다. 완료 이벤트 51개(빈 실행인 들여쓰기 오류 1개 포함)와 실행 오류 5개로 기존 분류 31/18/1/6이 유지됐다. 전체 소스 폴더는 Python 63개, 노트북 4개이며 이 페이지의 범위는 3단원 120–153쪽이다. 153쪽 학생 심화와 지도서 심화는 동일 코드지만 기존 감사와 연결하기 위해 별도 항목으로 유지한다.

공개 페이지에는 원본이 아닌 자체 제작 연계 코드 56개와 소량 UTF-8 데이터를 제공한다. 원본 오류 6개는 수정 이유를 표시하고 실행 가능한 자체 제작 코드를 사용한다. 전체 실행 결과는 `textbook-examples-report.md`에 기록한다.

새 콘텐츠를 작성하면서 `for … else` 미지원, 중첩 첨자의 복합 대입 오류, 정수값 실수의 출력 표기 차이를 확인했다. 이번 단계는 인터프리터를 바꾸지 않으며 공개 예제는 일반 조건문·일반 대입·명시적 소수점 형식으로 해당 학습 개념을 표현했다. 원본 56개 분류에 새 실패를 추가하는 항목은 아니다.

감사일: 2026-09-11 (13단계 교육용 turtle Canvas 추가 후 56개 재검사)

대상: `3단원/120쪽`부터 `3단원/153쪽`까지의 학생용 `.py` 56개. `지도서 심화.py`도 같은 153쪽 소스로 별도 기록했다. 원본은 읽기만 했고, 원본 경로에 쓰기·이동·삭제를 하지 않았다. 파일 입출력은 매 실행마다 분리된 앱 가상 파일 공간에서만 수행했다.

## 실행 방법과 기록 기준

- `input()`에는 정상 흐름을 확인하는 대표값을 순서대로 제공했다. 예: 139쪽 퀴즈에는 정답 5개, 145쪽 메뉴에는 메뉴 보기·주문·결제·종료 순서를 제공했다.
- 56개 모두 컴파일·VM 실행을 시도했다. 난수 게임은 VM별 초기 엔트로피 1234를 주입하고 정답을 제공했다. 입력 공급은 최대 20회, 기존 VM 반복·출력 제한은 변경하지 않았다. 153쪽 turtle은 Worker 그래픽 명령으로 실행했다.
- 실제 complete 이벤트는 51개다. 그중 149쪽 들여쓰기 오류로 아무것도 실행하지 않는 파일 1개를 교과서 오류로 별도 분류하여, 정상 예제 31개 + 입력 예제 18개 + 데이터 파일 필요 예제 1개 = 50개로 집계했다.
- 출력 칸은 실제 출력의 짧은 요약이다. 원본 전체 코드나 데이터는 이 보고서에 포함하지 않았다.

## 발견해 수정한 인터프리터 결함

한글 변수명·함수명·클래스명은 Python 식별자로 유효하지만, 기존 lexer가 ASCII 영문과 밑줄만 식별자로 읽었다. 이 때문에 121쪽 `함께 해결하기 1번`이 첫 줄에서 컴파일되지 않았다.

- lexer 식별자 판정을 Unicode 문자·숫자 속성으로 변경했다. 예약어 판정과 기존 ASCII 동작은 유지한다.
- `이름 = "정수연"` 및 `나이 = 17`을 실제로 실행하는 회귀 테스트를 추가했다.
- 수정 후 해당 121쪽 예제를 재실행해 성공을 확인했다.

따라서 최종 분류 6번은 0개다. 이 결함은 수정 전 감사에서는 1개였고, 수정 후 재검증에서 해소됐다.

## 10단계에서 추가한 문법

- 리스트 내포: `for`·`if` 필터·여러 `for`·반복 대상 언패킹·중첩 내포를 지원하며, 반복 변수는 바깥 범위에 남지 않는다.
- 첨자를 포함한 언패킹 대입: 오른쪽 값을 먼저 검증·확정한 뒤 왼쪽 대상을 순서대로 저장한다. 값 개수가 맞지 않으면 저장하지 않는다.
- f-string 형식 지정: `<`, `>`, `^` 너비, 정수 0 채움, 실수 `.Nf`를 지원한다.
- 세미콜론 단순문: 같은 줄의 단순문, 마지막 세미콜론, 주석과 빈 문장을 지원한다. 복합문 연결은 계속 거부한다.

## 아직 지원하지 않는 기능 우선순위

교육용 turtle 하위 집합은 13단계에서 지원했다. 키보드·마우스 이벤트, 애니메이션 콜백, 이미지 도형, 복제, 다중 화면, 사용자 정의 Screen 이벤트 루프와 전체 turtle 표준 라이브러리는 범위 밖이다. EUC-KR 쓰기·추가·바이트 내보내기도 지원하지 않으며 UTF-8을 사용하도록 명확히 안내한다.

11단계에서 random 5개 API와 datetime.date를 추가했다. 일반 모듈·외부 패키지, 전체 random API, datetime.datetime, 시간대·날짜 간격은 범위 밖으로 유지한다.

## 11단계 수정·검증 기록

- date는 유효 연월일만 생성하며 윤년과 값 비교를 지원한다. 제품 today는 현지 날짜, 테스트는 VM 시계 공급자를 사용한다.

- f-string 내부 오류의 줄 번호가 1로 초기화되는 문제를 발견해 원본 토큰 위치를 전달했다. 원본 149쪽의 오류 원인(미정의 속성)은 교과서 오류이며 인터프리터 결함으로 집계하지 않는다.

## 12단계 EUC-KR 검증 기록

- 자동 감지는 UTF-8 BOM, 엄격한 UTF-8, 엄격한 EUC-KR 순서다. 앱 내부와 Worker에는 디코딩된 Unicode 문자열만 전달한다.
- IndexedDB를 버전 2로 올리고 기존 레코드의 이름·내용·수정 시각을 유지한 채 `encoding: "utf-8"`과 실제 UTF-8 바이트 크기를 보충한다. 새로 가져온 파일은 선택·감지된 인코딩과 원본 바이트 크기를 함께 저장한다.
- Python `open()`의 EUC-KR·EUC_KR·CP949 별칭은 읽기 모드만 지원한다. EUC-KR 쓰기·추가는 명시적인 ValueError로 거부하고 내보내기는 계속 UTF-8이다.
- 직접 작성한 29바이트 EUC-KR CSV를 UTF-8 엄격 디코딩 실패와 EUC-KR 성공으로 확인했다. 로컬 Edge 360×800에서 자동 가져오기, 한글 파일명, 저장·재열기, 온라인·오프라인 `민수 90 / 지수 95` 출력, 대화상자 viewport 내부 배치를 확인했다. 서버 쓰기 요청은 0건이었다.
- F: 원본 15,084바이트 CSV를 EUC-KR로 디코딩해 124쪽 예제를 실제 재실행했다. 전체 56개 결과는 complete 50, 교과서 코드 오류 5개, 미지원 turtle 1개이며 인터프리터 결함은 0개다. 이 수치는 12단계 시점 기록이며 아래 13단계 재검사에서 갱신됐다.
- 기존 185개를 유지하고 EUC-KR·마이그레이션 전용 테스트 28개를 추가했다. 최종 213개 테스트와 `/pycom/` 프로덕션 빌드가 모두 통과했다.
- 최종 커밋은 `f50435893e637a88499222297283306b1909e8a6`이며 main에 일반 push했다. [GitHub Actions #34573595243](https://github.com/ljyoon1104-code/pycom/actions/runs/34573595243)의 설치·테스트·빌드·Pages 배포가 모두 성공했다.
- [실제 Pages](https://ljyoon1104-code.github.io/pycom/)를 Edge 360×800에서 검증했다. HTTP 200, 자동 가져오기, IndexedDB 저장·재열기, Service Worker 오프라인 재로드에서 모두 `민수 90 / 지수 95`를 출력했다. JavaScript 오류·정적 자원 실패·서버 쓰기 요청은 각각 0건이었다.
